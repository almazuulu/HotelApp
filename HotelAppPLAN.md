# План разработки HotelApp — модульный монолит для одной гостиницы

## 1. Архитектура и структура проекта

Приложение реализуется как модульный монолит: один Django/DRF backend, одна PostgreSQL-база и отдельный React SPA в одном репозитории. Docker-контейнеры являются средой запуска, а не микросервисами.

```text
HotelApp/
├── backend/
│   ├── config/                 # settings, urls, ASGI/WSGI
│   ├── apps/
│   │   ├── accounts/           # пользователи, профиль, session auth
│   │   ├── content/            # CMS гостиницы и главной страницы
│   │   ├── inventory/          # категории, комнаты, amenities, блокировки
│   │   ├── bookings/           # доступность, брони, холды, demo-платежи
│   │   └── inquiries/          # обращения из формы контактов
│   ├── tests/
│   ├── requirements/
│   ├── Dockerfile
│   └── manage.py
├── frontend/
│   ├── src/
│   │   ├── app/                # router, providers, API client
│   │   ├── features/           # auth, rooms, bookings, payments
│   │   ├── pages/
│   │   ├── shared/             # UI, hooks, types, utilities
│   │   ├── assets/
│   │   └── styles/
│   ├── Dockerfile
│   ├── package.json
│   └── package-lock.json
├── Hotelier_Template/          # исходный шаблон как reference
├── docker-compose.yml
├── .env.example
├── .gitignore
└── README.md
```

- Backend: Python 3.13, Django 5.2 LTS, DRF 3.17, PostgreSQL 17, drf-spectacular.
- Frontend: React 19.2, TypeScript, Vite, React Router, TanStack Query, React Hook Form, React-Bootstrap и Bootstrap 5.3.
- Node.js 22 LTS используется только для сборки, dev-server и frontend-тестов.
- Выбранные линии поддерживаются официальными проектами: [Django](https://www.djangoproject.com/download/), [DRF](https://www.django-rest-framework.org/community/release-notes/), [React](https://react.dev/versions), [Node.js](https://nodejs.org/en/about/previous-releases), [PostgreSQL](https://www.postgresql.org/support/versioning/).

## 2. Доменная модель и бизнес-правила

- `User` расширяет `AbstractUser`: вход по `username`, обязательный уникальный email, имя, фамилия и телефон. Клиенты не имеют доступа в Django admin.
- `HotelProfile` — singleton с названием, описанием, контактами, временем заезда 14:00/выезда 12:00, footer и SEO.
- Фиксированный CMS включает hero-слайды, блок «О гостинице», преимущества и контактный контент. Макет блоков задаёт React; произвольный HTML и page builder отсутствуют.
- `RoomType` содержит название, slug, описание, цену USD за ночь, `max_adults`, `max_children`, площадь, число кроватей, amenities, галерею и режим подтверждения `automatic/manual`.
- `Room` представляет физическую комнату с уникальным номером. Клиент бронирует категорию; конкретную комнату назначает backend и не раскрывает её номер в публичном API.
- Внутренний `RoomOccupancy` объединяет активные брони и служебные блокировки. PostgreSQL `DateRangeField` и `ExclusionConstraint` с `btree_gist` запрещают пересечение интервалов одной комнаты на уровне БД.
- Периоды считаются полуоткрытыми: `[check_in, check_out)`, поэтому выезд и следующий заезд могут быть в один день.
- Поиск принимает даты, количество взрослых и детей; категория подходит только при соблюдении обоих лимитов.
- Допустимы 1–30 ночей, горизонт — 365 дней. После 14:00 нельзя создать бронь с заездом сегодня.
- Цена фиксирована у категории. В бронь сохраняются снимки цены за ночь, итоговой суммы и контактных данных клиента.

Статусы брони:

- `pending_confirmation` — ручная заявка, удерживает комнату до 24 часов, но не позже 14:00 дня заезда.
- `awaiting_payment` — автоматическая бронь или одобренная менеджером заявка; срок demo-оплаты 30 минут, но не позже времени заезда.
- `paid` — demo-оплата успешно завершена.
- `rejected`, `cancelled`, `expired` — терминальные состояния.
- Отдельный `completed` не создаётся: прошлая бронь определяется по дате выезда или терминальному статусу.

Модуль бронирования предоставляет единый глубокий интерфейс: поиск доступности, расчёт цены, создание, подтверждение/отклонение, demo-оплата, отмена и истечение. Внутри него:

- операция создания выполняется в `transaction.atomic()`;
- категория и кандидаты-комнаты блокируются, доступность повторно проверяется;
- quote не резервирует комнату;
- `Idempotency-Key` защищает от двойного клика;
- конкурентная попытка на последний номер возвращает `409 ROOM_UNAVAILABLE`;
- просроченные холды освобождаются при поиске, создании и чтении брони; также предоставляется команда `expire_bookings`, без Redis/Celery;
- клиент может отменить бронь до 00:00 даты заезда по `Asia/Bishkek`;
- отмена оплаченной брони переводит demo-платёж в `refunded`;
- изменение дат или категории не поддерживается — создаётся новая бронь.

## 3. Интерфейсы, UI и админка

REST API версионируется через `/api/v1/`, использует Django session cookie, CSRF и единый формат ошибок `{code, message, errors}`. Деньги передаются строками Decimal, даты — ISO 8601.

| Область | Интерфейсы |
|---|---|
| Auth | CSRF, регистрация, login/logout, `GET/PATCH me`, запрос и подтверждение сброса пароля |
| CMS | `GET /site/` с профилем гостиницы, hero, преимуществами, контактами, footer и SEO |
| Каталог | список категорий с фильтрами, детали по slug, quote с доступностью и итоговой ценой |
| Брони | создание, список `active/history`, детали по reference, отмена, demo-оплата |
| Контакты | публичное создание обращения |
| Документация | OpenAPI schema и Swagger UI |

Frontend-маршруты:

- Главная, каталог, детали категории, «О гостинице», контакты.
- Вход, регистрация, восстановление пароля.
- Защищённые страницы создания брони и demo-оплаты.
- Кабинет: профиль, активные брони, история и детали брони.
- Статусы обновляются при открытии/возврате на вкладку и периодически на странице активной брони.
- Demo-форма карты явно обозначена как учебная. PAN/CVV не отправляются на backend и не сохраняются; endpoint получает только `{method: "demo_card"}`.
- Интерфейс полностью русский, адаптивный и доступный с клавиатуры.

Django admin:

- Менеджер управляет CMS, каталогом, комнатами, блокировками, бронями, demo-платежами и обращениями.
- Контент-редактор видит CMS, тексты, изображения, amenities и маркетинговые поля категорий, но не видит брони, платежи, клиентов и коммерческие поля.
- Подтверждение, отклонение и отмена брони выполняются admin actions. Статус, даты, цена и назначенная комната не редактируются напрямую.
- Обращения имеют статусы «новое/обработано».
- `seed_demo` идемпотентно создаёт группы, CMS, три категории, комнаты, amenities и тестовые аккаунты из переменных окружения.

Шаблон `Hotelier_Template` переносится как дизайн-система: палитра, типографика, hero и карточки. jQuery, Owl Carousel, WOW.js и Bootstrap-4 Tempus Dominus удаляются; используются React-Bootstrap Carousel и нативные date inputs. В footer сохраняется обязательная атрибуция HTML Codex.

## 4. Docker и локальный запуск

`docker-compose.yml` поднимает:

- `db` — PostgreSQL с healthcheck и постоянным volume;
- `backend` — Django dev server с hot reload, миграциями, media-volume и доступом к `/admin/`, `/api/`, `/schema/`, `/docs/`;
- `frontend` — Vite dev server с hot reload и proxy для `/api` и `/media`.

`.env.example` содержит настройки БД, Django secret, timezone, demo-пользователей и разрешённые hosts. Реальный `.env`, media и данные PostgreSQL игнорируются Git.

README описывает:

1. копирование `.env.example`;
2. `docker compose up --build`;
3. `seed_demo`;
4. адреса React, Django admin и Swagger;
5. команды миграций, тестов и линтеров.

Nginx, Gunicorn, S3, Redis, Celery, SMTP, production-compose и облачный деплой в MVP не входят. Сброс пароля использует стандартные Django-токены и console/file email backend.

## 5. Проверка и критерии готовности

Backend-тесты:

- расчёт ночей, USD-цены и snapshot-полей;
- отдельные лимиты взрослых и детей;
- пересечения, соседние даты, служебные блокировки;
- автоматический и ручной режимы;
- 24-часовой холд и 30-минутный срок оплаты;
- конкурентное бронирование последней комнаты и DB exclusion constraint;
- идемпотентность повторного POST;
- подтверждение, отказ, истечение, отмена и demo-refund;
- запрет доступа к чужим броням;
- session/CSRF и права менеджера/редактора;
- сохранение и обработка обращений.

Frontend-тесты:

- формы поиска, регистрации, бронирования и профиля;
- route guards и отображение ошибок API;
- статусы, таймер оплаты, отмена;
- проверка, что карточные данные не попадают в HTTP-запрос.

Playwright E2E:

1. автоматическая бронь → demo-оплата → отображение в кабинете;
2. ручная заявка → подтверждение менеджером → оплата клиентом;
3. отмена оплаченной брони → освобождение номера и demo-refund.

Готовность подтверждается тем, что чистый запуск Docker, миграции и seed проходят по README; доступны React, admin и Swagger; все проверки, TypeScript, ESLint, Ruff и тесты проходят; две параллельные операции не могут забронировать одну комнату на пересекающиеся даты.

## Зафиксированные ограничения

- Одна гостиница, одна валюта USD, часовой пояс `Asia/Bishkek`.
- Нет реальных платежей и email-уведомлений о бронях.
- Нет гостевого бронирования, нескольких комнат в одной брони, сезонных цен, промокодов и мультиязычности.
- Нет reception/PMS, паспортных данных, check-in/check-out операций и изменения существующей брони.
- Приложение предназначено для локального учебного использования, но критическая доменная логика и защита от двойного бронирования реализуются корректно.
